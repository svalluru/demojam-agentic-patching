Presenter's guide

Before you open the door

  • Start the console and leave it on the CVE list with nothing run yet — beat 1 depends on the diagram still being grey.
  • Know what is under the page before you are asked. The Agent trace in the left column names every service the run called and every one that did not answer, and /tmp/demo-backend.log carries the same record. Read it once beforehand so you are not reading it for the first time in front of anybody.
  • Close this drawer with Esc. You can reopen it mid-run — it does not disturb anything.
  • The flow icon between this book and the gear is one diagram per side of the toggle, and it reads left to right the way the run happens: the stages across the middle, the product each one calls in the lane above, the approval gate, and the recovery arc over the top. Every box names who does it — the Supervisor, one of the four agents, common code, or you — and every arrow carries its step number on one side of the line and what happens at that step on the other, so you can put a finger on one arrow and read only that. It takes the whole window, because ten columns of this need the room, and it opens on the side you are already on. That is the thing to put up when somebody asks what is actually happening, rather than drawing it on a whiteboard mid-demo.
  • The colours are a second slide inside the first one. Red is a Red Hat product, blue is an agent we run, amber is the one stage a person decides, and the key is printed under the drawing so you never have to explain it. A stage takes the colour of whoever runs it, not of what it calls — which is why Score stays blue while both boxes it reaches are red. Point at the Infrastructure diagram and the story reads itself: everything blue is ours, the red is Red Hat underneath it, and there is exactly one amber box between them. Application has no blue, because there are no agents on that side — say that out loud rather than skipping it — but its spine is red end to end, Lightwell through to AAP.
  • On a projector, set Text size to Large in the gear panel. It is a browser setting — nothing is sent to the server and nobody else's view changes.
  • Budget 12 minutes for the eight beats below, plus questions. The short version is beats 1, 2, 4 and 7. If you only have time for one side, drop beat 6.

The sentence it all hangs off

Patching is not slow because applying a patch is slow. It is slow because deciding which hosts to patch, and getting a person to agree, takes longer than the patch does. This puts an agent on the deciding and keeps the person on the agreeing.

If you say one thing, say that. Everything below is evidence for it.

Run of show

1

The system, before anything runs 30s

DoPoint at the left panel. Nothing has run yet, so every box is grey.
Say“That is the whole system — a supervisor, the agents it drives, and the services behind them. Two of the agents are not built, which is why they are dashed, and they will still be dashed at the end. Everything else lights up as it gets called.”
Lead with this because it is the one claim nobody else can make from a slide: the diagram is drawn from the agents' own event log, not from a drawing of what the flow is supposed to be. Say that out loud — it is the difference between a demo and an animation.
2

Assess the critical CVE 90s

DoPress Assess on the CVE-2024-3094 row. Then stop talking and let the left panel move.
Say“Insights hands over the CVE and the affected hosts. The supervisor wakes the first agent, which goes to the risk model and to the patch history store, both of those in parallel. Every line you just watched light up is a logged call. If one of those boxes had stayed grey, nothing would have asked it.”
The pause is the point. People expect a spinner; what they get is a system describing itself while it works. Do not narrate over it.
3

Read the plan like a reviewer would 90s

DoWalk the plan: the maintenance window, the counts, then the score per host against the gate line.
Say“One question here: which of these do we send. Every bar is past the gate, so all five need a person — and what that person reads comes up on the next screen, next to the button they press.”
DoPoint at the dispatch button before you press it. It reads Send 5 for approval, in black.
Say“The button is labelled from the verdict. It never says patch when it is not about to patch anything.”
4

The gate — the beat that sells it 2 min

DoSend the five. Approve one host. Watch its bar fill. Leave the others sitting at the gate.
Say“Every host got its own workflow run and every one of them stopped. Nothing moves until somebody approves it. That bar is the fraction of workflow steps that have reported finished — it is not a timer. If the run stalls, the bar stalls.”
DoApprove the rest. One of them comes back Not verified instead of green. Stop there.
Say“Every step of that run went green and the host is still vulnerable. The last step goes back to the machine and asks, and the advisory is still listed. A console that read patched off the job exited zero would have told you this one was done.”
DoPress Fix & retry on that row. Point at the pre-filled drain timeout before you press Retry this host, then approve it again.
Say“The thirty-second drain expired with connections still open, so the package transaction never ran. Those numbers are not a fleet default — they are this host's own history, the same record the plan scored it from. Same gate, second run, and now it verifies.”
Say the bar line to an ops audience specifically. They have all been lied to by a progress bar, and volunteering that yours is measured buys more credibility than the rest of the demo put together. The not-verified host is worth the same honesty: a demo where everything works is a demo nobody believes, and this is the failure the last workflow step exists to catch.
5

The other path: no gate at all 60s

DoGo back to the list and assess CVE-2024-1086.
Say“Lower severity, both hosts under the threshold, so there is no approval gate anywhere downstream. Notice the button went red and now says Patch 2 hosts — because that press is the only human check these hosts get. Nothing stops to ask again.”
Shows the routing is a real decision rather than a fixed script, and that the console changes its own language depending on the consequence. Also worth pointing at: Reasoning stays grey on this one, because no host needed review so nothing ever asked it.
6

The other half: patch what the code depends on 2 min

DoSwitch the header toggle to Application. Tick JoyChou93/java-sec-code — any listed repository works — and scan it. The stage bar above changes with you: same two rows, different eight stages.
Say“Same console, same gate, different unit of work. A host has a CVE; a repository has a dependency, and the dependency has the CVE. This reads the manifests, asks OSV.dev what is known about every version in them, and then asks Lightwell whether there is a build that fixes it without moving anyone off the version they are on.”
DoOpen a repository, press Plan a fix, read the change list, then Approve and run. While it builds, point at the stages.
Say“Plan a fix launches nothing — it is a preview, and the exact list of version changes is on screen before anybody approves anything. Approve and run clones it, applies that list and builds it. It stops at built and verified. Nothing has been pushed.”
DoIt fails. Let the red land, then read the amber line underneath it out loud.
Say“The build broke, and the console is not hiding it. A Lightwell rebuild keeps the version number and the API, but it is compiled to a supported Java baseline — and this project still compiles for 8. That next step is read out of Maven's own output, not out of anything we knew in advance.”
DoPress Change the choices and run again, set Java for the build to 11, and approve it.
Say“Nothing was pushed, because there was nothing worth pushing — the Push button never appeared. One control, one re-run, and this time it goes green.”
DoNow press Push branch and let them notice how quick it is.
Say“Second approval, and it does not build again — the build that went green is the one it pushes. It re-applies the same change list, checks the tree hashes to the diff that was verified, and only then pushes. If it did not match, it would stop: a branch nobody built is worse than no branch.”
This is the beat that turns a patching demo into a platform one. Say the Lightwell line slowly — “fixed without changing the version you run” is the part that is genuinely hard to do elsewhere, and the diff on screen is the proof. The push being quick is not a detail: it is why a second approval is affordable at all. The failed build is the same move as the not-verified host in beat 4, on the other side of the console: the gate holds, the broken thing never leaves the build host, and the way forward is one named control rather than a ticket.
7

What it saved 2 min

DoPress Calculate ROI, top right of the header. Say where the timings came from before you touch a number — the page will not say it for you.
Say“Both halves of the console on one page, each against its own baseline — same arithmetic, different work, and they are added in hours and money and in nothing else. There is no total of hosts and repositories anywhere on it, because that number would mean nothing.”
DoPoint at Still left by hand in Where the effort goes. It is on whichever side you ran, and it is the segment worth volunteering before anybody finds it.
Say“The manual column costs the whole job — every repository scanned, every host the CVE affects — so everything the run did not finish is priced at the manual rate and charged back against us. Find thirty, fix six, and the page will not let you claim the saving on thirty. A host counts only when it reports patched: one nobody ticked, one that failed and one somebody rejected are all still vulnerable, and all three are charged.”
Say“The measured half is this run's own clock. The manual half is assumed — it has to be, because the manual run never happened. So the first card is a slider for every assumption behind the comparison. If you think fifteen minutes of change prep per host is generous, drag it down now and the whole page follows.”
DoHand the laptop over and let them move a slider. If you do one interactive thing all demo, do this one.
Say“Further down it tells you how far those assumptions have to move before the conclusion flips, and the payback card says outright that the platform cost is the weakest number on the page.”
DoScroll slowly to the black card, What this is up against — the bars sweep and the dots fill as it comes into view, so arriving mid-animation is the effect. This is the card to land on; do not rush past it. Trace the 43 days bar, then the stub underneath it that is this run.
Say“Everything above this card was our arithmetic. Nothing on this one is. The top bar is Verizon's median across thirteen thousand organisations, the hatched one is CISA's deadline, and the bar at the bottom is this run — drawn at the minimum width the chart can render, because it is too small to draw.”
DoThen the dots. Pause and let them count.
Say“Sixty-five in a hundred known-exploited vulnerabilities are still open a week later. Verizon's own words for that are a possible theoretical ceiling for human remediation processes — maturity, investment, tooling, all measured, none of them move it. This is the one you cannot hire your way past.”
DoDrop to Measured, not modelled and point at the pink line: this page's own baseline is 14× faster than that median, so the saving above is understated, not inflated.
DoThen How the industry sees this, and read the last paragraph — the one about 40% of agentic projects being cancelled — out loud. Do not skip it.
A savings page nobody can argue with is a page nobody believes. Handing over the sliders converts the most sceptical person in the room into the one operating it — and raising the strongest objection yourself, from the same analyst you just quoted in your favour, is what buys the rest of it.
8

Close on what was real 20s

DoSwitch back to Infrastructure and point at the Agent trace in the left column, which has been building the whole time.
Say“Every hop you just watched is in that list, in order, with the seconds between them — and each one names the service it called and what came back. The diagram and the trace are drawn from the same event log, so the two cannot disagree with each other, and neither of them can disagree with what actually ran.”
Close on the trace, because it is the only part of the demo the room can audit for itself, and offering that is worth more than another claim. It also answers the question that was coming anyway — whether what they saw is what happened — before anybody has to ask it.

If they ask

“Is any of this real?” The agents, the control flow, the approval gate, the thresholds and the routing rules are, and the trace under the diagram is every call they made — so you can check that rather than take it from me. Which hosts and which repositories it is pointed at is configuration, not code.
“What happens when one of your backends is down?” Writes fail closed: a patch is never assumed. That asymmetry is deliberate — a missing risk score can be worked around and a missing patch cannot. And nothing is silent: whatever happened to a step is in the Agent trace and in the backend log, named service by service, so a gap is something you point at rather than something somebody finds later.
“Can it patch without a human?” Yes, below the threshold, and the threshold is a setting — the gear at the top right. Show them. Being able to move the line between supervised and unattended in front of them is more convincing than any claim about where it sits.
“Where does the patch history come from?” A vector store — Milvus with Llama Stack in front of it — queried per host, and only for hosts that need review. The model is XGBoost, served on OpenShift.
“How do we know the agent did what you say it did?” The trace under the diagram is every hop, in order, with the seconds between them, and the API carries the same list. Scroll it. It is the same source the diagram draws from, so the two cannot disagree.
“Can we change the thresholds and the costs?” Gear icon, every tunable the process reads, grouped, with its default shown until something overrides it. In-memory and lost on restart; .env is the durable place.
“Why not just upgrade every dependency to the latest version?” Because that is the upgrade nobody has time to test. Lightwell builds the fix back onto the version you already run, so the change list moves patch levels and not majors — and the exact list is on screen before anyone approves it.
“Does it merge the fix?” No. It pushes a branch, and your existing review and CI decide from there. There are two approvals before even that: Approve and run to build it, and Push branch once the build is green.

Do not say

  • Do not call the ROI figures a measured saving. Half of that comparison is assumed and the page says so. Claiming otherwise is the one thing on here that would be caught later rather than in the room.
  • Do not claim the risk score discriminates between hosts yet. Three of its four inputs describe the CVE rather than the host, so hosts of one CVE score almost alike. It needs tuning, and saying so costs you nothing.
  • Do not let a clean screen stand in for a check. The page does not mark where a value came from; the Agent trace does, and so does the log behind it. If you are asked whether a number was measured, read the trace rather than the card. Saying so costs twenty seconds; being caught not saying it costs the whole demo and not just that slide.
  • Do not call a green build a guarantee the application still works. It is the repository's own mvn verify: it compiles and its tests pass. That is why the run stops at a branch and your review and CI take it from there — claim the branch, not the release.
  • Do not promise the infrastructure workflow against a controller nobody has set up. Two of the three job templates it calls belong to the lab and exist nowhere else, so pointing it at a customer's own Automation Orchestrator fails part way through an approved run. Check what is there before you offer it.
  • Do not present agents 3 and 4 as coming soon with a date. They are not started. The diagram already shows them dashed; let it.
  • Do not divide this run's exposure window by 43 days and quote the multiple. It is a five-figure number that rests entirely on the assumed side of the comparison. The page prints the two durations and no ratio on purpose — do the same.
  • Do not turn the $4.99M breach cost into a saving. Nothing here avoided a breach, and nobody in the room will let you multiply it by a probability you made up. It is on the page for scale and it is in no total.
  • Check the dates on the cited figures before you present. They are baked in — the console makes no network calls — so they do not refresh themselves. Quoting last year's DBIR as this year's is the kind of slip the one analyst in the room will catch.

Between demos

Delete the run store and reload — rm -f runs/simulated.json — otherwise the ROI page's lifetime card carries your last rehearsal into the next room. Everything else is in memory and comes back clean when you restart the console.

The one thing a restart does not undo is a branch that was pushed. Delete it before the next run, or the next Push branch lands on a branch that already exists.
